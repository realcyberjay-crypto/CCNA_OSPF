FoundationsCONCEPT

What OSPF Is

OSPF (Open Shortest Path First) is the industry-standard link-state interior gateway protocol. Unlike RIP’s “routing by rumour,” every OSPF router builds a complete map of the area and runs the Dijkstra SPF algorithm to compute its own shortest path to every network.

RIP passes along gossip; OSPF hands everyone the same map. Each router draws the identical picture of the network, then works out the best road for itself — so it converges fast and doesn’t believe bad rumours.

Why engineers reach for it

  • Open standard (RFC 2328) — works across every vendor, unlike Cisco’s EIGRP.
  • Scales to large networks (areas keep the SPF work and flooding contained).
  • Fast convergence — changes are flooded immediately and SPF re-runs.
  • Efficient — hellos and updates go to multicast, not broadcast.
  • Every router holds a complete topology map of its area.

Metric is cost (derived from bandwidth), and the administrative distance is 110 — more trusted than RIP (120), less than EIGRP (90).

FoundationsCONCEPT

Link-State Fundamentals

OSPF and IS-IS are the two link-state IGPs. The idea is simple and powerful:

  • Each router describes its own interfaces and directly connected neighbours in a Link-State Advertisement (LSA).
  • LSAs are flooded unchanged from router to router until every router in the area holds the same information — the Link-State Database (LSDB).
  • With an identical map, each router independently runs SPF to find its own best path.

This is the key contrast with distance vector: OSPF routers never trust a neighbour’s summary of the world. They exchange raw facts (LSAs), build an identical database, and each does its own maths.

How OSPF WorksPROCESS

The OSPF Process (6 Steps)

From cold start to a populated routing table, OSPF follows the same sequence:

  1. Discover neighbours — send and listen for Hello packets on each OSPF-enabled interface.
  2. Form adjacencies — with neighbours whose Hello parameters match.
  3. Exchange & flood LSAs — build the shared LSDB for the area.
  4. Run SPF (Dijkstra) — calculate the shortest path to every network.
  5. Install best routes — put the winners into the routing table.
  6. React to change — on any topology change, re-flood, re-run SPF, update the table.

Hellos never stop — they’re also the keepalive. Miss enough (the dead interval, 4× hello by default) and the neighbour is declared down, triggering a new SPF run.

Neighbour & Adjacency States

Before two routers reach Full, the adjacency climbs through a sequence of states. Knowing them makes troubleshooting obvious — a stuck state points straight at the fault.

How OSPF WorksDR / BDR

Designated & Backup Designated Routers

On a multi-access link (an Ethernet segment with several routers), OSPF elects a Designated Router (DR) and a Backup DR (BDR). Instead of every router flooding to every other (n² adjacencies), all routers form full adjacencies only with the DR/BDR — collapsing the mesh into a star.

Election

  • Highest OSPF interface priority wins (default 1).
  • Tie → highest Router ID.
  • Priority 0 = never DR/BDR.
  • It’s per-segment, and not preemptive — a later, higher-priority router won’t steal the role until the next election.

On point-to-point links there is no DR/BDR — the two routers simply go Full directly.

See the Adjacencies group for the election rules in full, the network types that decide whether an election happens at all, and what actually occurs when the DR or BDR fails.

The Seven States, Told as a Story

Two routers becoming neighbours follows the same arc as two people meeting in a dark room: shout, get a reply, confirm they heard your name, agree who talks first, compare notes, fill the gaps, done. Every OSPF state is one beat of that story — and knowing which beat you're stuck on tells you exactly what's broken.

224.0.0.5 is the public address system — everyone hears it. 224.0.0.6 is the direct line to the chair and vice-chair. You shout to the room to find people; once you know them, you speak to them directly; and when you have news for the group, you tell the chair and let them announce it.

Hello also does the ongoing health check

After the adjacency is up, Hellos keep flowing every 10 seconds on broadcast and point-to-point links. Miss 4 in a row — the 40-second dead interval — and the neighbour is declared down, SPF re-runs, and the routing table changes. (On NBMA the defaults are 30 and 120.)

R1(config-if)# ip ospf hello-interval 5
R1(config-if)# ip ospf dead-interval 20   faster detection — must match on BOTH ends

Changing the hello interval on IOS auto-adjusts the dead interval to 4× the hello on that interface — but only on that interface. The neighbour keeps its old values and the adjacency drops, because hello and dead intervals must match to form a neighbour at all. Change both ends in the same window.

The must-match list

These parameters are compared in the Hello. Any one of them wrong and the neighbour never forms:

  • Area ID — both interfaces in the same area
  • Hello and Dead intervals — must be identical
  • Subnet and mask — both interfaces on the same IP subnet
  • Authentication — type and key
  • Stub / NSSA flag — the area type must agree
  • Unique Router IDs — two routers sharing a RID will not form an adjacency

And one that is not in the Hello but breaks things later: MTU. It's carried in the DBD, which is why an MTU mismatch lets you get all the way to ExStart/Exchange before failing — the most confusing failure mode OSPF has, because the neighbour appears in the table.

The MTU trap, in detail

R1# show ip ospf neighbor
Neighbor ID     Pri   State      Dead Time   Address     Interface
172.16.2.1        1   EXSTART/ -  00:00:33    10.0.0.2    FastEthernet0/0
                      <- appears, never reaches FULL, cycles endlessly

R1# show interface FastEthernet0/0 | include MTU
  MTU 1500 bytes, BW 100000 Kbit
R2# show interface FastEthernet0/0 | include MTU
  MTU 1460 bytes, BW 100000 Kbit

Proper fix — make the MTUs match:

R2(config)# interface FastEthernet0/0
R2(config-if)# ip mtu 1500

Workaround — when you don't control the far end (a carrier handoff, a partner device):

R1(config)# interface FastEthernet0/0
R1(config-if)# ip ospf mtu-ignore   skip the MTU check in the DBD

mtu-ignore suppresses the symptom, not the cause. The adjacency comes up, but if a genuinely oversized LSU now needs to cross that link it will be dropped, and you get an LSDB that won't converge — a far harder problem to diagnose than a stuck ExStart. Use it to restore service, then fix the MTU properly.

The one you'll actually use: p2p on Ethernet

Most "point-to-point" links in a modern network are Ethernet — a /30 or /31 between two routers, or a routed uplink to a core switch. OSPF still calls that broadcast and dutifully elects a DR and BDR between two routers, which is pointless. Override it:

AdjacenciesWHY A DR

Why a Shared Segment Needs a Chairman

Point-to-point is simple: two routers, one adjacency, done. Put five routers on one Ethernet segment and let every pair form a full adjacency, and the arithmetic turns ugly fast.

It's a boardroom. Without a chair, twelve people all talk to each other at once and the same news gets repeated a dozen times. With a chair, you tell the chair, and the chair announces it to the room. The BDR is the vice-chair — sitting through every meeting, taking the same notes, ready to take over the instant the chair walks out.

The three roles

RoleJob
DRThe focal point for the segment. Every router forms a full adjacency with it, sends it changes, and it replicates them out to everyone. It also originates the Type 2 Network LSA for the segment.
BDRListens to everything, stays fully synchronised, takes over instantly if the DR fails. It does not replicate updates while the DR is alive.
DROTHEREveryone else. Full adjacency with the DR and BDR only — and 2-Way with each other, permanently.

How updates actually travel

DirectionAddressWho listens
DROTHER reports a change up224.0.0.6 (AllDRouters)Only the DR and BDR
DR announces it down224.0.0.5 (AllSPFRouters)Every OSPF router on the segment

Two DROTHERs sitting at 2-Way is not a fault — it's the entire point of the design. They know each other exists (which is enough for SPF, since the Type 2 LSA describes the segment) but they never exchange databases directly. If you see 2WAY/DROTHER in show ip ospf neighbor, that line is healthy.

No DR is elected on point-to-point links — with only two routers there's no mesh to collapse. They go straight to Full, and no Type 2 LSA is generated.

AdjacenciesELECTION

Winning the Election — and Reading the Result

The election happens at the 2-Way state, per segment, and follows three rules in order.

  1. Highest interface priority wins the DR seat; second-highest becomes BDR. Range 0–255, default 1.
  2. Tie is broken by the highest Router ID. With everything at the default priority, the RID decides — which is why the "wrong" router so often ends up as DR.
  3. Priority 0 disqualifies that interface entirely. It can never be DR or BDR, no matter who else fails.

Where the tie-break number really comes from. Every interface has priority 1 by default — there is no such thing as "unset" — so on an untouched network every router ties and the Router ID decides. And the RID itself is usually derived from the highest loopback address. Chain it together: loopback IP → Router ID → DR. On a default-priority network the DR is effectively whoever has the highest loopback — chosen by accident of addressing rather than by design. Set the priority where the DR matters.

The election is non-preemptive. Bring a shiny new router with priority 255 onto a segment where a priority-1 router is already DR, and nothing happens — the incumbent keeps the seat. Priority only decides the next election, which happens when the DR is lost or the OSPF process is restarted. This surprises people constantly: they set the priority, check, and conclude the command didn't work.

Configuring the outcome you want

! ---- force R1 to be DR ----
R1(config)# interface FastEthernet0/0
R1(config-if)# ip ospf priority 100

! ---- disqualify R4 permanently (e.g. an underpowered branch box) ----
R4(config)# interface FastEthernet0/0
R4(config-if)# ip ospf priority 0

! ---- force the election to re-run (non-preemptive, remember) ----
R1# clear ip ospf process
Reset ALL OSPF processes? [no]: yes

clear ip ospf process drops every adjacency on the router and blackholes traffic until they rebuild. It's the correct tool here because nothing else will dislodge a sitting DR — but it belongs in a change window, not in a live-troubleshooting reflex. Clearing on the DROTHERs first, and the current DR last, minimises the disruption.

Choose your DR deliberately: the most stable, least loaded router on the segment, and ideally not a box that reboots for other reasons. Left to defaults, the DR is whichever router happens to have the highest RID — which is to say, chosen at random.

ConfigurationCONFIG

Basic Configuration

Enabling single-area OSPF takes two ideas: start the process, then tell it which interfaces to run on with network statements.

R1(config)# router ospf 1   start OSPF, process-id 1
R1(config-router)# network 10.0.0.0 0.0.0.255 area 0   match interfaces in 10.0.0.x, put in area 0

What network ... area does

  • Scans the router’s interfaces; any whose IP falls inside address + wildcard is enabled for OSPF.
  • On a matched interface it sends/receives Hellos (to form neighbours) and advertises that interface’s subnet.
  • area 0 places it in the backbone.

The network statement itself isn’t what gets advertised — the interface’s actual subnet is. The statement just selects which interfaces participate.

ConfigurationPROCESS ID

Process ID — Locally Significant

The number after router ospf is the Process ID. It’s locally significant — it does not need to match your neighbour to form an adjacency.

  • Different interfaces can run in different OSPF instances — each instance has its own LSDB.
  • Normally you run one process per router.

Process IDs not matching between neighbours is fine. But running two different processes on the same router (top row above) keeps their databases isolated — R1 and R3 never learn each other’s routes even though R2 is adjacent to both. The fix is a single unified process (bottom row).

R2(config)# router ospf 1
R2(config-router)# network 10.0.0.0 0.0.0.255 area 0   toward R1
R2(config-router)# network 10.1.0.0 0.0.0.255 area 0   toward R3 — same process = routes shared
ConfigurationWILDCARD

Wildcard Masks

OSPF’s network statement uses a wildcard mask — an inverted subnet mask. Work it out by subtracting each octet from 255:

Subnet maskWildcardReads as
255.255.255.0 (/24)0.0.0.255match first three octets, ignore the last
255.255.255.252 (/30)0.0.0.3match all but the low 2 bits
255.255.0.0 (/16)0.0.255.255match first two octets only

So network 10.0.0.0 0.0.255.255 area 0 enables OSPF on any interface starting 10.0.x.x — handy to switch on several interfaces with one line. Use 0.0.0.0 to match a single exact IP.

ConfigurationAUTHENTICATION

OSPF Authentication

Without authentication, anything that can send a Hello onto your segment can become an OSPF neighbour and inject routes. On an access layer or anywhere a port might be reached by something you don't control, that's a real exposure — a rogue router advertising a better cost can pull traffic through itself.

TypeNameVerdict
0Null (none)The default. No protection.
1PlaintextThe key travels in clear text in every Hello. Stops accidents, not attackers.
2MD5The key is never transmitted — only a hash. Use this one.

Per-interface (MD5) — the common approach

R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip ospf message-digest-key 1 md5 MySecretKey   key ID 1
R1(config-if)# ip ospf authentication message-digest

R2(config)# interface GigabitEthernet0/0
R2(config-if)# ip ospf message-digest-key 1 md5 MySecretKey   same key ID AND same key
R2(config-if)# ip ospf authentication message-digest

Per-area — apply to every interface in the area at once

R1(config)# router ospf 1
R1(config-router)# area 0 authentication message-digest   turns it on area-wide
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip ospf message-digest-key 1 md5 MySecretKey  the key is still per-interface

The area command sets the mode; the key is always configured on the interface. Turning on area authentication without putting keys on the interfaces drops every adjacency in that area — which is exactly as disruptive as it sounds. Push the keys first, then enable the mode.

Verify

R1# show ip ospf interface GigabitEthernet0/0 | include authentication|Message
  Message digest authentication enabled
    Youngest key id is 1

R1# show ip ospf neighbor       still FULL = the keys match
R1# debug ip ospf adj
OSPF: Rcv pkt from 10.0.0.2, Gi0/0 : Mismatch Authentication Key - No message digest
OSPF: Rcv pkt from 10.0.0.2, Gi0/0 : Mismatch Authentication Key - No 'ip ospf authentication'

Authentication is checked in the Hello, so a mismatch means no neighbour at all — not a stuck state, just silence. If you enable it and a neighbour vanishes, that's the first thing to check, and the debug above names the exact problem. Both the key ID and the key string must match; matching keys under different key IDs will still fail.

Rolling a key without an outage: configure the new key ID on both ends while the old one is still in place. IOS sends packets with every configured key during the overlap, so the adjacency survives — then remove the old key ID from both ends.

How OSPF Cost Is Calculated

OSPF's metric is cost, and it is derived from one thing only: the bandwidth value the software believes an interface has. Each interface gets a cost; SPF adds up the costs of the outbound interfaces along a path, and the lowest total wins.

cost = reference bandwidth ÷ interface bandwidth
     = 100,000,000 bps ÷ interface bandwidth (bps)      default reference = 100 Mbps
  • The result is rounded down to an integer.
  • The minimum cost is 1 — anything at or above the reference bandwidth lands on 1.
  • Only outbound interface costs are counted; the receiving interface on the far end is irrelevant.

Default costs at the default reference bandwidth

InterfaceBandwidthCost

FastEthernet100 Mbps1
GigabitEthernet1 Gbps1 ← same as Fast

Metric blindness. Because cost bottoms out at 1, a default OSPF process cannot tell a 100 Mbps link from a 10 Gbps link — it will happily load-share across both as equal-cost paths. On any modern network you must raise the reference bandwidth.

Raising the reference bandwidth

R1(config)# router ospf 1
R1(config-router)# auto-cost reference-bandwidth 100000   value is in Mbps → 100 Gbps
% OSPF: Reference bandwidth is changed. Please ensure reference bandwidth is consistent across all routers.

That warning is not decoration. The reference bandwidth must be identical on every router in the OSPF domain — mismatch it and two routers compute different costs for the same link, which produces suboptimal paths and, on asymmetric topologies, routing loops. Change it everywhere, in one maintenance window.

Overriding a single interface directly

R1(config)# interface FastEthernet0/0
R1(config-if)# ip ospf cost 50   hard-set the cost; ignores bandwidth entirely

ip ospf cost beats everything — reference bandwidth, bandwidth, physical speed. It's the blunt, explicit tool for steering traffic when you don't want to lie about an interface's bandwidth (which would also mislead QoS and EIGRP).

Cost & MetricsPHYSICAL vs LOGICAL

speed vs clock rate vs bandwidth

Three commands that look interchangeable and are not. Two of them change what the wire actually does; the third changes what the software believes — and only the third one touches OSPF.

CommandLayerWhereEffect
speedPhysicalEthernet interfacesForces the real line rate (e.g. a FastEthernet port down from 100 to 10 Mbps). Real throughput changes.
clock ratePhysicalSerial, DCE end onlySets the real clocking on a serial link (e.g. down from T1's 1.544 Mbps to 64 Kbps). Real throughput changes.
bandwidthLogicalAny interfaceA software-only declaration in Kbps. Feeds OSPF cost, EIGRP metric and QoS. Moves no packets faster or slower.

speed and clock rate are the engine. bandwidth is the number written on the speedometer. Change the speedometer and the car doesn't go any faster — but every decision made by someone reading it does change.

Worked example — both layers, one interface

! ---- physical layer: change what actually moves ----
R1(config)# interface FastEthernet0/0
R1(config-if)# speed 10              link now really runs at 10 Mbps

R1(config)# interface Serial0/0/0
R1(config-if)# clock rate 64000      serial now really clocks at 64 Kbps (DCE end)

! ---- logical layer: tell the software the truth ----
R1(config)# interface FastEthernet0/0
R1(config-if)# bandwidth 10000       10,000 Kbps = 10 Mbps → cost 100/10 = 10

R1(config)# interface Serial0/0/0
R1(config-if)# bandwidth 64          64 Kbps → cost 100,000/64 = 1562

This is the trap. Setting speed 10 on its own does not reprice the link for OSPF — a FastEthernet interface keeps reporting a bandwidth of 100,000 Kbps to the software, so OSPF still calls it cost 1 while the wire crawls at 10 Mbps. You have to set bandwidth as well. Throttling the physical layer and forgetting the logical layer is how traffic ends up pouring down your slowest link.

Which way does the number move the cost?

  • Higher bandwidth → lower cost → the interface becomes more attractive to SPF.
  • Lower bandwidth → higher cost → SPF steers traffic away from it.
  • It's an inverse relationship because bandwidth is the denominator in the cost formula.

Why you'd touch bandwidth at all

  • Truth-telling. A subrate circuit — a serial port physically clocked at 64 Kbps, or a 100 Mbps handoff on a Gig port from the carrier — reports the wrong default. Correcting bandwidth makes OSPF's arithmetic match reality.
  • Policy. Nudging a path to be preferred or avoided without changing hardware.
  • QoS. WFQ, CBWFQ and priority reservations all size their queues from the logical bandwidth — get it wrong and you'll reserve percentages of a number that doesn't exist.

If you only want to influence routing and nothing else, prefer ip ospf cost over bandwidth. Changing bandwidth is a side-effect machine: it silently re-rates EIGRP metrics and QoS reservations on the same interface too.

How Costs Add Up Along a Path

SPF doesn't compare links — it compares whole paths. For every destination it walks each candidate path, adds up the cost of the interfaces it would send out of, and installs the lowest total. Three rules make the arithmetic predictable:

  1. Outbound only. Only the cost of the interface a packet leaves is counted. The receiving interface at the far end contributes nothing to that direction's total.
  2. Include the last hop. The cost of the interface on the destination's own router that faces the target subnet is part of the sum. A LAN hanging off R1 is not free — R1's LAN interface cost is added.
  3. Cost is per-direction. Because only outbound interfaces count, R2→R1 and R1→R2 are two independent calculations. Set them differently and you get asymmetric routing: traffic leaves one way and returns another.

Intra-area vs inter-area arithmetic

Inside your own area the router has the full LSDB, so it computes the cost end to end itself. For a destination in another area it can only compute the cost as far as the ABR, then add the cost the ABR advertised in its Type 3 LSA — it is trusting someone else's arithmetic for the far half of the journey.

Route typeWhat the local router computed
O (intra-area)The whole path, from its own LSDB, link by link.
O IA (inter-area)Cost to reach the nearest ABR + the metric that ABR advertised. No visibility past the border.

Equal-cost load balancing. If two paths tie on total cost, OSPF installs both and load-shares (4 paths by default, up to 16 with maximum-paths). This is worth knowing before you tune: a cost change that accidentally creates a tie will split your traffic rather than move it.

R2# show ip route 10.0.1.0                 the winning path and its total cost
R2# show ip ospf interface brief           every local interface's cost, in one screen

Worked Example 2 — Metric Blindness in Action

Same triangle, but now the direct R2→R1 link is FastEthernet and the path through R3 is Gigabit. Nothing is misconfigured — and OSPF still sends everything down the slow link, purely because of the default reference bandwidth.

Why the default breaks

Cost is reference ÷ bandwidth with a floor of 1. At the default 100 Mbps reference, everything from FastEthernet upwards computes to 1 — so a 100 Mbps link and a 1 Gbps link are indistinguishable, and the shorter path simply wins on hop count by accident. Here the two-hop Gigabit path totals 3 against the direct link's 2, so OSPF picks the slow one and stays there.

Note that the last term is 1000 in both tuned paths — R1's LAN interface toward 10.0.1.0/24 is FastEthernet either way, so it's a constant. The decision is made entirely by the transit links, which is exactly what you want.

The global fix

R1# configure terminal
R1(config)# router ospf 1
R1(config-router)# auto-cost reference-bandwidth 100000   in Mbps → 100 Gbps
R1(config-router)# end
R1# write memory

Every router, no exceptions. Reference bandwidth is a local calculation, not something exchanged in an LSA — a router that missed the change keeps computing costs on the old scale, and the two disagree about which path is best. Pick a value high enough for your fastest future link (100000 covers up to 100 Gbps at cost 1) and roll it out domain-wide in one window.

[110/1200] is the proof: the metric matches the tuned-reference calculation and the next hop is now the Gigabit neighbour. If you still see [110/2], the reference change hasn't been applied on this router — check show ip ospf first, not the interfaces.

Default OSPF is a map that stops labelling roads once they're wider than two lanes — motorway, dual carriageway and B-road all look the same, so it just picks the one with fewest junctions. Raising the reference bandwidth is putting the road classifications back on the map.

Traffic EngineeringEXAMPLE 1

Example 1 — Steering with ip ospf cost (and the asymmetry trap)

The requirement: the R4–R5 link is a cheap backup circuit. You want production traffic on the R3–R2 chain, and R5 used only if that chain fails.

Step 1 — make the backup expensive on R4

R4(config)# interface FastEthernet2/0
R4(config-if)# ip ospf cost 100   the link toward R5
Path (R4 → 10.0.1.0/24)Cost beforeCost after
via R3 → R244 ✓ now chosen
via R53 ✓100 + 1 + 1 = 102

One command, one interface, and outbound traffic moves. The R5 path is still in the LSDB and fully usable — if R4's FE0/0 goes down, SPF re-runs and 102 becomes the best available cost. That's a proper backup, not a disabled link.

Step 2 — check the return path (this is where people get burned)

Cost is per-interface and per-direction. R1 computing its way back to R4's LAN never looks at R4's FE2/0 cost at all — it looks at its own outbound interfaces:

Path (R1 → 10.1.2.0/24)Outbound interfacesCost
via R5R1 FE3/0 (1) + R5 FE2/0 (1) + R4 FE1/0 (1)3 ✓ still chosen
via R2 → R3R1 FE0/0 (1) + R2 FE1/0 (1) + R3 FE0/0 (1) + R4 FE1/0 (1)4

Step 3 — fix it at the other end of the same link

R5(config)# interface FastEthernet2/0
R5(config-if)# ip ospf cost 100   the same physical link, the other end

Now R1's return options become 1 + 100 + 1 = 102 via R5 versus 4 via R2 — and both directions take the R3–R2 chain. The rule to carry away:

A link has two costs, one per end. Tuning a path means tuning both ends of every link you're steering around — otherwise you've only moved half the conversation.

Why asymmetry matters more than it used to. Routing-wise, asymmetric paths work fine. Anything stateful in the path does not: a firewall that sees the SYN but never the SYN-ACK has no session to match the return traffic against and drops it. The same applies to NAT, IPS/deep inspection, and flow-based load balancers. On a network with inline security devices, asymmetry isn't untidy — it's an outage waiting for the next TCP handshake.

Scope check before you commit

ip ospf cost on R5's FE2/0 changes that interface's cost for every destination reached through it, not just this one. Before applying, ask what else routes out of that interface — on a transit router, the answer is often "more than you expected". If only one prefix should move, cost is the wrong tool; use a route-map/policy or reconsider the design.

Rollback

R4(config-if)# no ip ospf cost   returns to the bandwidth-derived value

R1(config)# router ospf 1

This is the one lever that cannot create asymmetry — as long as you apply it everywhere. Applying it to some routers is worse than applying it to none. A. The carrier handoff that lies about its speed

Scenario: the R1–R5 link is a 20 Mbps metro-Ethernet service delivered on a FastEthernet port. The port says 100 Mbps; the contract says 20. OSPF believes the port, so it costs the link as if it were five times faster than it is.

R1(config)# interface FastEthernet3/0
R1(config-if)# bandwidth 20000   20,000 Kbps = 20 Mbps — the truth
R5(config)# interface FastEthernet2/0
R5(config-if)# bandwidth 20000   both ends, always
ReferenceCost before (port speed)Cost after (real speed)
100 Mbps default1100,000,000 / 20,000,000 = 5

Use bandwidth when the number is wrong and you're correcting it; use ip ospf cost when the number is right and you simply want a different preference. The distinction matters because bandwidth is also read by QoS — correcting it fixes your queue sizing at the same time, whereas abusing it to steer traffic silently corrupts that sizing.

B. Deliberate equal-cost load sharing

Sometimes you want both paths. If you cost them to match, OSPF installs both and load-shares — by default across up to 4 paths, on a per-destination (CEF per-flow) basis rather than per-packet.

R4(config)# interface FastEthernet2/0
R4(config-if)# ip ospf cost 2       make the 2-hop path total 4, matching the 3-hop path

R4# show ip route 10.0.1.0
  Known via "ospf 1", distance 110, metric 4
  Routing Descriptor Blocks:
  * 10.1.1.2, from 1.1.1.1, via FastEthernet0/0
    10.1.3.2, from 1.1.1.1, via FastEthernet2/0   <- two next hops installed

R4(config-router)# maximum-paths 2   default 4; set explicitly if you want a hard cap

Load sharing and stateful devices are an uneasy pair. CEF keeps a given flow on one path, so a single TCP session stays consistent — but the forward and return flows can still hash onto different paths, which is asymmetry again. If there's a firewall in the middle, prefer a single deterministic path.

Traffic EngineeringVERIFY + METHOD

Verifying a Path Change — Both Directions

A path change isn't verified until you've proved it from both ends. Checking only the router you configured is how asymmetry ships to production.

The method

  1. Baseline first. Capture show ip route <dest> and a traceroute from each end before you touch anything. You cannot prove an improvement you didn't measure.
  2. Do the arithmetic on paper. Write down the expected cost of both paths, both directions. If the router's metric doesn't match your number afterwards, one of your assumptions about an interface is wrong.
  3. Apply on the correct interface — the one traffic leaves, on both ends of the link.
  4. Verify the interface took the cost, then verify the route moved, then verify the return.
  5. Traceroute both ways and compare. Same routers in reverse order = symmetric.

The commands, in order

CommandWhat it proves
show ip ospf interface briefThe cost landed on the interface you meant. Fastest first check.
show ip ospf interface fa2/0The cost in full context — area, network type, neighbour count.
show ip route <prefix>The winning next hop, the exit interface, and the total metric.
show ip route ospfEverything OSPF installed — useful for spotting collateral damage to other prefixes.
traceroute <dest>The path packets actually take, not the one the table implies.
show ip ospf neighborThat your change didn't drop an adjacency.
show ip ospf database router <rid>The per-link costs a router is advertising to everyone else.
show ip cef exact-route <src> <dst>Which path a specific flow takes when several are installed.

The traceroute pair — the proof that counts

R4# traceroute 10.0.1.1
  1 10.1.1.2 4 msec      R3
  2 10.1.0.2 8 msec      R2
  3 10.0.0.1 12 msec     R1

R1# traceroute 10.1.2.1
  1 10.0.0.2 4 msec      R2
  2 10.1.0.1 8 msec      R3
  3 10.1.1.1 12 msec     R4

Read the two traceroutes as one picture: R3, R2, R1 going out and R2, R3, R4 coming back — the same routers in reverse order. That, and only that, is what symmetric means. If the hop lists don't mirror each other, you have more work to do regardless of what the routing table says.

Two habits worth keeping. Source your test traffic correctly — traceroute 10.0.1.1 source 10.1.2.1 tests the path a user takes; a plain traceroute uses the router's own outgoing interface IP and can follow a different route entirely. And avoid clear ip ospf process to "make changes apply": cost changes take effect on their own within seconds. That command resets every adjacency on the router and will drop live traffic.

If the route didn't move

  • Cost applied to the wrong interface — remember it's the interface traffic leaves, not the one it arrives on.
  • A more specific route wins — longest prefix match happens before any cost comparison. Check with show ip route <host address>.
  • The prefix is inter-area — you can only influence the cost up to the ABR; the rest is whatever the ABR advertised.
  • Another protocol is winning on AD — a static route at AD 1 doesn't care what OSPF thinks.
  • The metric changed but the path didn't — you probably haven't beaten the alternative yet. Re-check your arithmetic against show ip ospf interface brief on every hop.

How the Router ID Is Chosen

Every OSPF router needs a unique 32-bit Router ID (written like an IP). It picks one in a strict order:

  1. Manually configured router-id — always wins.
  2. Else, the highest IP on any Loopback interface.
  3. Else, the highest IP on any active physical interface.

A loopback is preferred even if its IP is lower than a physical interface — because a loopback never goes down, the RID stays stable. That’s why best practice is a loopback or a manual RID.

No loopback — RID from highest physical IP

R1# show ip protocols
  Router ID 10.0.3.1   <- highest physical IP
  Distance: (default is 110)

Add a loopback — it takes over (even though 1.1.1.1 is lower)

R1# show ip int brief
Loopback0    1.1.1.1    YES manual up up

R1# show ip protocols
  Router ID 1.1.1.1   <- loopback wins

The RID is chosen once at startup. Adding a loopback (or changing the RID) later does not take effect until you reset the process:

R1# clear ip ospf process   Reset ALL OSPF processes? [no]: yes

Setting the Router ID

Best practice is to set it explicitly so it never drifts:

R1(config)# router ospf 1
R1(config-router)# router-id 1.1.1.1
R1# clear ip ospf process   required for the new RID to take effect

Changing a RID is disruptive (it resets adjacencies), so choose it once and leave it. A common convention is a loopback like 1.1.1.1 that also doubles as a management/anchor address.

Passive Interfaces

A passive interface keeps advertising its subnet into OSPF but stops sending Hellos out of it — so no adjacency can form there. No hellos means no neighbour.

Where to use it

  • Loopbacks — there’s no neighbour to find (OSPF wouldn’t hello out them anyway, so it’s belt-and-braces).
  • Stub / user LANs — advertise the subnet, but stop a rogue router forming an adjacency.
  • Partner links — e.g. toward R6, if it’s handled by static routing instead.
R1(config)# router ospf 1
R1(config-router)# passive-interface Loopback0
R1(config-router)# passive-interface FastEthernet2/0   no adjacency with R6

Flip the default when most interfaces should be passive

R1(config-router)# passive-interface default   make ALL interfaces passive
R1(config-router)# no passive-interface FastEthernet0/0   ...then re-activate the few that peer
R1(config-router)# no passive-interface FastEthernet3/0

passive-interface default is the clean pattern on a router with many user ports and only one or two real neighbours — deny by default, allow explicitly.

Default Route InjectionDEFAULT

Injecting a Default Route

Rather than typing a default route on every router, you configure the exit once on the edge router (R4) and let OSPF advertise it to everyone.

R4(config)# ip route 0.0.0.0 0.0.0.0 203.0.113.2   the real default toward the ISP
R4(config)# router ospf 1
R4(config-router)# default-information originate   advertise that default into OSPF

R4 becomes the office’s “front door.” You don’t walk to every desk (R3, R2, R1) writing down directions to the exit — R4 announces “unknown traffic? send it to me” and the whole network learns the way out automatically.

Verify on R1 — look for O*E2

R1# show ip route
Gateway of last resort is 10.0.0.2 to network 0.0.0.0

O*E2  0.0.0.0/0 [110/1] via 10.0.0.2, 00:00:01, FastEthernet0/0
O     10.1.1.0/24 [110/51] via 10.0.0.2, FastEthernet0/0

O = OSPF, * = candidate default, E2 = external type-2 (injected from outside OSPF). Seeing O*E2 0.0.0.0/0 confirms R1 learned the internet exit dynamically.

Multi-Area OSPFCONCEPT

Why OSPF Uses Areas

In a single-area network every router holds a full link-state map of every router and every link. That is fine at ten routers. At two hundred, one flapping link on the far side of the estate forces every router to re-flood LSAs and re-run SPF — burning CPU and memory across the whole network for a change nobody else cares about.

Areas are OSPF's containment walls. A change inside an area is flooded and recalculated only inside that area; the rest of the network just keeps using the summary it already had.

Think of a large office block. Area 0 is the lift shaft and corridors — nobody lives there, everything passes through it. Each floor is its own area: if a desk moves on floor 3, floor 7 doesn't need a new floor plan. It just needs to know "floor 3 is that way, via the lift."

The two kinds of area

AreaRole
Area 0Backbone / transit area. Normally carries no end users — it exists to move traffic between areas. All inter-area traffic passes through it.
Area 1, 2, 3…Regular / non-backbone areas. Where the end users and access layer live. Each attaches to area 0 through an ABR.

The rules that keep it sane

  • Every non-backbone area must touch area 0 — traffic from area 1 to area 2 goes area 1 → area 0 → area 2, never directly.
  • Area 0 must be contiguous. A split backbone breaks inter-area routing (a virtual link is the sticking-plaster fix).
  • Adjacencies only form between routers in the same area — the area ID is checked in the Hello, so an area mismatch on a link means no neighbour at all.
  • Routers with all OSPF interfaces in area 0 are backbone routers; routers with all interfaces in one non-zero area are internal routers.

Small networks don't need this. If you have a handful of routers, put everything in area 0 and move on. Areas are a scaling tool, and they cost you design complexity — spend it only when the SPF/flooding load or the routing-table size justifies it.

Multi-Area OSPFROLES

Router Roles: Internal, Backbone, ABR, ASBR

A router's "role" in OSPF isn't configured — it's simply a consequence of where its interfaces sit. One router can hold more than one role at the same time.

RoleDefinitionWhat it produces
InternalAll OSPF interfaces in one non-backbone area.Type 1 router LSAs inside its own area.
BackboneAt least one interface in area 0.Type 1 LSAs into area 0.
ABRInterfaces in two or more areas, one of which is area 0.Type 3 summary LSAs — it re-advertises the networks of one area into the other. These arrive as O IA.
ASBRRedistributes routes from outside OSPF (EIGRP, BGP, static, connected) into OSPF.Type 5 external LSAs — these arrive as O E1 or O E2.

An ABR is the receptionist between two floors — it doesn't tell floor 1 where every desk on floor 0 is, it just says "everything on floor 0 is through me." An ASBR is the loading dock at the back of the building: it's the only way goods from outside the company get in.

These roles stack. A router can be an ABR and an ASBR at once (an area-1 border router that also has an ISP static default and runs default-information originate is exactly that).

Multi-Area OSPFLSDB

What Each Router Actually Knows

This is the single most important idea in multi-area OSPF: the LSDB stops at the area boundary. A router builds a full, link-by-link topology map of its own area only. Everything beyond that arrives pre-chewed from the ABR as a list of reachable prefixes with a cost — no link detail, no SPF.

So what does an area-1 router hold?

  • A complete LSDB of area 1 — every router, link, and cost. It runs Dijkstra across this.
  • Type 3 summaries for area 0 and every other area, learned from its ABR, installed as O IA routes.
  • Type 5 externals (if an ASBR exists anywhere), installed as O E1 / O E2. These flood across all normal areas untouched.

The scaling win is really two wins: smaller LSDB (less memory, faster SPF) and contained flooding (a link flap in area 2 never disturbs area 1's SPF). Summarisation on top of that shrinks the routing table as well.

Inter-area routes are not free. Because area routers only see the ABR's advertised cost, they can't compare the two areas' internal paths themselves — suboptimal routing through a badly placed ABR is a classic multi-area design bug, and summarisation can hide the more specific detail that would have fixed it.

Multi-Area OSPFCONFIG

Configuring the Two-Area Lab

Nothing new syntactically — the area keyword on the end of the network statement is doing all the work. On an ABR you simply write two network lines with two different area numbers.

R1 — internal, area 1

R1(config)# router ospf 1
R1(config-router)# router-id 1.1.1.1
R1(config-router)# network 10.0.0.0 0.0.255.255 area 1   every 10.0.x.x interface → area 1

One line covers FE0/0 (10.0.0.1), FE3/0 (10.0.3.1) and both user stubs, because the wildcard 0.0.255.255 ignores the last two octets.

R2 — ABR (area 0 + area 1)

R2(config)# router ospf 1
R2(config-router)# router-id 2.2.2.2
R2(config-router)# network 10.1.0.0 0.0.0.255 area 0   FE1/0 toward R3 → backbone
R2(config-router)# network 10.0.0.0 0.0.0.255 area 1   FE0/0 toward R1 → area 1

Note the tight /24 wildcards here. If you'd used 0.0.255.255 on R2 like you did on R1, the same interface could be caught by both statements and land in the wrong area. On a border router, be specific.

R3 — backbone

R3(config)# router ospf 1
R3(config-router)# router-id 3.3.3.3
R3(config-router)# network 10.1.0.0 0.0.1.255 area 0   catches 10.1.0.1 and 10.1.1.2 in one line

R4 — backbone

R4(config)# router ospf 1

R4(config-router)# network 10.1.1.0 0.0.0.255 area 0   link to R3
R4(config-router)# network 10.1.2.0 0.0.0.255 area 0   user stub
R4(config-router)# network 10.1.3.0 0.0.0.255 area 0   link to R5

R5 — ABR (area 0 + area 1)

R5(config)# router ospf 1

R5(config-router)# network 10.0.3.0 0.0.0.255 area 1   area 1 link down to R1

Multi-Area OSPFVIRTUAL LINKS

Virtual Links — the Emergency Patch

Two rules keep multi-area OSPF coherent: every area must touch area 0, and area 0 must be contiguous. A virtual link is what you reach for when one of those has already been broken and you can't immediately fix the cabling.

Configuration — on both ABRs

! ---- ABR-A (RID 2.2.2.2), through transit area 1, to ABR-B ----
ABR-A(config)# router ospf 1
ABR-A(config-router)# area 1 virtual-link 3.3.3.3   the FAR router's Router ID

! ---- ABR-B (RID 3.3.3.3), pointing back ----
ABR-B(config)# router ospf 1
ABR-B(config-router)# area 1 virtual-link 2.2.2.2

Read the command as: "through area 1, reach the router whose RID is 3.3.3.3." The area number is the transit area you're crossing — not area 0, and not the orphaned area. That's the part people get backwards.

Verify

ABR-A# show ip ospf virtual-links
Virtual Link OSPF_VL0 to router 3.3.3.3 is up
  Run as demand circuit, Transit area 1, via interface Gi0/1, Cost of using 2
  Hello 10, Dead 40, Wait 40, Retransmit 5

ABR-A# show ip ospf neighbor
Neighbor ID   Pri  State     Address    Interface
3.3.3.3         0  FULL/  -  10.1.0.2   OSPF_VL0   <- the virtual interface

The rules and the caveats

  • Both endpoints must be ABRs, and the transit area must have full routing (no partial reachability).
  • The transit area cannot be a stub or NSSA. Type 5 LSAs have to cross it, and a stub area refuses them.
  • Area 0 cannot be the transit area — that would be circular.
  • The endpoints are identified by Router ID, so a RID change on either side breaks it silently.

Treat a virtual link as a temporary repair, not a design. It hides a structural problem behind logical configuration: the next engineer sees a working network with no obvious sign that area 2 is reachable only because of two lines of config on routers they may never look at. Use it to restore service during an outage or a migration, then fix the underlying topology — a real link into area 0, or a redesign of the area boundaries — and remove it.

SummarizationABR SUMMARY

Summarising at the ABR — area range

By default an ABR generates one Type 3 LSA per prefix — area 1's four /24s become four O IA routes in area 0. Summarisation collapses them into a single advertisement before they cross the border.

The plan for our lab

R2(config-router)# area 1 range 10.0.0.0 255.255.0.0   collapse area 1's subnets before sending them into area 0
R2(config-router)# area 0 range 10.1.0.0 255.255.0.0   collapse area 0's subnets before sending them into area 1

R5(config)# router ospf 1
R5(config-router)# area 1 range 10.0.0.0 255.255.0.0
R5(config-router)# area 0 range 10.1.0.0 255.255.0.0

Configure it identically on every ABR out of that area. With two doors (R2 and R5), summarising on only one means area 0 keeps hearing the specific /24s from the other — and longest-prefix-match will pull all the traffic toward the unsummarised ABR. Asymmetric summarisation is a classic cause of "why is everything going the long way round?"

Reading area X range

  • area 1 range means "networks that originate in area 1, summarise them as they leave." It is not "advertise this into area 1."
  • The mask here is a normal subnet mask (255.255.0.0), not a wildcard — unlike the network statement. Easy trap.
  • It only affects Type 3 (inter-area) LSAs. Routers inside area 1 still see all four specific /24s.

The ABR is the receptionist again. Instead of reading out all four desk numbers on floor 1 to everyone in the lift lobby, she says "floor 1 — anything starting 10.0, it's through me." Fewer words, same outcome, and she doesn't have to shout an update every time a desk moves.

Reading the Routing TableANATOMY

Anatomy of a Route Line

Every line in show ip route follows the same shape. Read it left to right and it answers: how did I learn this, what is it, how much do I trust it, how far is it, and where do I send the packet?

The bracket, in detail

PartMeans
110Administrative distance — how believable the source is, used only when two protocols offer the same prefix. OSPF is always 110. Lower wins (connected 0, static 1, EIGRP 90, OSPF 110, RIP 120).
2000Metric (OSPF cost) — the sum of the outbound interface costs along the path. Used to pick between two OSPF paths to the same prefix. Lower wins.

AD is compared first, metric second — and only ever within the same protocol. Comparing an OSPF cost of 2000 against an EIGRP metric of 3072 is meaningless; the AD decides that fight before the metric is even looked at.

Before any of this, longest prefix match wins outright. A O 10.0.2.0/24 beats a O IA 10.0.0.0/16 for a packet to 10.0.2.5 regardless of AD or cost — the more specific route is simply a better match. AD and metric are only tie-breakers between routes of equal prefix length.

Worked example — reading a real table

R1# show ip route
Gateway of last resort is 10.1.1.1 to network 0.0.0.0

O*E2   0.0.0.0/0 [110/1] via 10.1.1.1, 00:19:35, FastEthernet0/0
      10.0.0.0/8 is variably subnetted, 10 subnets, 2 masks
O IA     10.0.0.0/16 [110/2000] via 10.1.0.2, 00:18:18, FastEthernet1/0
O        10.1.2.0/24 [110/2000] via 10.1.1.1, 00:20:56, FastEthernet0/0
O        10.1.3.0/24 [110/2500] via 10.1.1.1, 00:16:07, FastEthernet0/0
      192.168.0.0/32 is subnetted, 3 subnets
O IA     192.168.0.1 [110/2001] via 10.1.0.2, 00:18:18, FastEthernet1/0
  1. O*E2 0.0.0.0/0 [110/1] — a default route from outside OSPF. Someone ran default-information originate; the cost of 1 is the flat E2 seed, and it would read the same on every router in the domain.
  2. O IA 10.0.0.0/16 — a /16 in a table full of /24s. That shape is the signature of an ABR summary. This router is not in that area and never saw its links.
  3. O 10.1.2.0/24 and O 10.1.3.0/24 — plain O, so both are in this router's own area, computed locally by SPF. The cost difference (2000 vs 2500) is real path cost this router worked out itself.
  4. "variably subnetted, 10 subnets, 2 masks" — a header, not a route. It's telling you the 10.0.0.0/8 space contains prefixes at two different mask lengths (/16 and /24) — which is your hint that summarisation is in play.
  5. O IA 192.168.0.1 under a /32 is subnetted header — a host route, almost always someone's loopback being advertised from another area.

Quick field heuristic: a prefix shorter than everything around it is a summary, IA means you're trusting an ABR's arithmetic, and E2 costs that are suspiciously round and identical everywhere are seed metrics, not distances.

Filtering the noise

R1# show ip route 10.0.2.5        which single route would this packet actually use?
R1# show ip route | include IA    just the inter-area routes

These two build the topology map inside a single area. Everything else in OSPF is bolted on top of them.

Type 1 — Router LSA

Every OSPF router originates exactly one Type 1 into each area it belongs to. It says "I am router X, here are my links, here is the cost out of each one, and here is who's on the other end." SPF is run over the collection of Type 1s (stitched together by Type 2s where needed).

Type 2 — Network LSA

A Type 2 exists only on a multi-access segment, and only the DR generates it. It represents the segment itself as a pseudo-node: "this Ethernet exists, and these routers are attached to it."

LSA TypesTYPE 3 & 4

Type 3 (Summary) and Type 4 (ASBR Summary)

Both are generated by ABRs, and both exist for the same reason: routers in one area need to reach things in another area without being given that area's topology.

Type 3 — Summary LSA

  • One per prefix the ABR is passing between areas (or one per area range if you've summarised).
  • Carries no topology — just prefix, mask and the ABR's cost to reach it.
  • Installs as O IA. The receiving router adds its own cost to reach the ABR, then adds the ABR's advertised cost.
  • Despite the name, it does not summarise anything by default — "summary" here means "condensed description", not "aggregate". Actual aggregation needs area range.

Type 4 — ASBR Summary LSA

This is the one that confuses people, so here's the exact problem it solves. R7 in area 1 receives a Type 5 external LSA that says "203.0.113.0/24, originated by 4.4.4.4." Type 5s flood unchanged across areas — so the advertising router is the ASBR's Router ID, not a next hop. R7 has never seen area 0's topology and has no idea where 4.4.4.4 is or how far. Without that, it cannot compute a cost and the external route is unusable.

So the ABR generates a Type 4: "router 4.4.4.4 is reachable through me, at cost N." Now R7 can do the arithmetic.

LSA TypesTYPE 5 & 7

Type 5 (External) and Type 7 (NSSA External)

Both carry routes that came from outside OSPF. The difference is purely which area the ASBR happens to be sitting in — and what that area's rules allow.

Type 5 — External LSA

  • Originated by the ASBR, and floods unchanged through every normal area — ABRs pass it along rather than rewriting it.
  • The Advertising Router field stays the ASBR's Router ID all the way, which is why the Type 4 is needed to locate it from other areas.
  • Installs as O E1 or O E2 (E2 default — flat seed metric; E1 adds internal cost).
  • Blocked at the border of stub, totally stubby, NSSA and totally NSSA areas.

Type 7 — NSSA External LSA

A stub area's whole premise is "no external LSAs in here." But sometimes you need an area to be stub-like and have its own small external connection — a branch with a local internet breakout, say. That contradiction is what NSSA (Not-So-Stubby Area) resolves.

  • Inside the NSSA, the local ASBR's externals travel as Type 7 — a different type number precisely so the "no Type 5 here" rule stays intact.
  • Installs locally as O N1 / O N2 (same costing logic as E1/E2).
  • At the NSSA's ABR, Type 7 is translated into Type 5 and flooded on into the rest of the domain. When several ABRs border the NSSA, the one with the highest Router ID does the translating.
  • The P-bit (propagate) in the Type 7 is what asks for that translation; if it's clear, the route stays local to the NSSA.

A stub area is a department that doesn't accept post from outside the company. NSSA is the same department that's been granted one exception — it may have its own back door, and its own mail goes out through reception (the ABR), which re-stamps it with the company letterhead so the rest of the business accepts it.

R6# show ip ospf database nssa-external    Type 7 — only visible inside the NSSA
R3# show ip ospf database external         Type 5 — including R5's translated version

R6# show ip route ospf

R3# show ip route ospf
O E2  172.16.9.0/24 [110/20] via 10.0.0.5, 00:03:20, GigabitEthernet0/0

That last pair is the clearest demonstration of the whole idea: one prefix, two LSA types, decided entirely by which side of the NSSA border you're standing on.

LSA TypesSTART HERE

Stub and NSSA in Plain English

Before the LSA-type tables, the one-sentence version: configuring an area as stub or NSSA tells the ABR to stop forwarding certain information into that area, and to hand down a default route instead.

That's genuinely all it is. No traffic is blocked. No link changes. It is purely about how much detail the routers inside that area are told.

Think of a satellite office with one road in and out.

You could give everyone there a full directory of every address in the company, every partner site, every supplier — thousands of entries, updated constantly. Or you could say: "here's the map of this office in full detail, and for anything else — out the front door, turn left."

The second one is a stub area. Nothing is lost in practice, because there's only one road out anyway. Knowing 4,000 external destinations doesn't help you when every one of them exits the same way.

What "configuring it" actually does

You type area 1 stub on every router in the area. Two things happen mechanically:

  • The ABR stops passing external routes (Type 5 LSAs) into the area.
  • The ABR generates a default route, 0.0.0.0/0, and sends that in instead.

Why NSSA exists

Stub has a side effect. Since the area refuses externals coming in, it also can't produce any going out — the rule has to work both ways or the design falls apart. So a stub area can't have its own connection to anything outside OSPF.

Then someone points out: our branch has a local internet line. Or a small link to a partner. We want the small-routing-table benefit and our own back door.

NSSA is the exception written into the rules. Same filtering — no externals from the rest of the world — but your own external connection is permitted. Its routes travel inside the area under a different label (Type 7) purely so the "no Type 5 in here" rule isn't violated, and the ABR relabels them on the way out so the rest of the network accepts them normally.

Stub is the office that doesn't accept post from outside the company. NSSA is that same office granted one exception — it may have its own back door, and its own mail goes out through reception, which re-stamps it with company letterhead so everyone else accepts it.

 In one sentence
Stub"Don't tell us about the outside world — just point us at the exit."
NSSA"Same, except we've got our own side door and we need to tell you about it."

Everything else — the LSA type numbers, the 7-to-5 translation, the P-bit — is just the machinery that makes those two sentences work. The sections that follow are that machinery; come back to this page whenever it stops making sense.

LSA TypesNSSA, DRAWN OUT

NSSA, Drawn Out — the Branch With Its Own Back Door

NSSA makes far more sense as a picture of a real business than as a rule about LSA types. Here's the situation that invented it.

Head office has the corporate internet circuit and connections to a couple of partners. The branch is small — a few routers, a handful of users, hardware that was cheap five years ago. You want the branch's routing table to stay tiny: its own subnets, and a default pointing at head office. That's a stub area, and it's the right call.

Then the branch gets a local broadband line for guest Wi-Fi and a small partner link. Suddenly the branch has its own connection to something outside OSPF — and a stub area is flatly not allowed to have one.

Read the picture in four statements

  1. Head office externals don't enter the branch. The ABR blocks Type 5, exactly as a stub would. The branch gets a default route instead. Small table achieved.
  2. The branch's own external is allowed — but it travels inside the branch as a Type 7, not a Type 5. Different label, so the "no Type 5 in here" rule is never broken.
  3. On the way out, the ABR re-stamps it — Type 7 becomes Type 5 — and it floods normally through the rest of the company.
  4. The same route has two names. On the branch router it's O N2. At head office it's O E2. Both correct, both the same destination.

The branch is a department that doesn't accept post from the outside world — everything comes via head office. Then it's granted one exception: it may have its own back door. Its outgoing mail still goes through reception, which puts it in a company envelope so everyone else accepts it as normal internal post.

Why not just make it a normal area?

Stub, Totally Stubby, NSSA — What Each One Blocks

The stub/NSSA flag is checked in the Hello packet. If one router in the area is missing area 1 stub, it will not form an adjacency with its neighbours at all — the symptom looks like a link problem, not a config mismatch. Configure it on every router in the area, including the ABR.

The rules that constrain you

  • Area 0 can never be stub or NSSA. It has to carry externals for everyone else.
  • A stub area cannot contain an ASBR — no Type 5 allowed in means no Type 5 originated inside either. Need one? That's exactly what NSSA is for.
  • A virtual link cannot cross a stub or NSSA area.
  • no-summary is configured on the ABR only — it's the ABR that stops sending, so the internal routers need no extra config.

Troubleshooting order when a route is missing

  1. Is the route in show ip route? No → check the database for the LSA that should carry it.
  2. Is the LSA in show ip ospf database in the right section? No → the problem is upstream: the originator isn't generating it, or an ABR is filtering it.
  3. Missing externals in one area only → check the area type (stub/NSSA blocks Type 5) and show ip ospf database asbr-summary for the Type 4.
  4. LSA present but no route installed → look for a better route from another protocol (AD), or a Type 4 gap making the external's cost uncomputable.

Knowing the failure behaviour turns a 2am page into a five-minute check. The most-asked case first.

Routing and path

CommandLook for
show ip route ospfRoute codes — O, O IA, O E1/E2, O N1/N2, O* — and the metrics in brackets.
show ip route <prefix>The winning entry after longest-prefix-match: next hop, exit interface, and total metric. Settles most arguments.
show ip route 0.0.0.0Whether a default exists and which code it carries — O*IA (stub substitute from an ABR) or O*E2 (from an ASBR).
show ip cef exact-route <src> <dst>Which path a specific flow takes when equal-cost paths are installed.

show log | include OSPF%OSPF-5-ADJCHG entries — when a neighbour dropped and why (dead timer, interface down, loading done).

Debug — and turning it off

CommandLook for
debug ip ospf hello"Mismatched hello parameters" and the line that follows naming the field — dead interval, hello interval, or area ID. The most direct answer to "why no neighbour".
debug ip ospf adjMaster/slave negotiation, "has larger interface MTU", DR/BDR election lines (Elect DR, DR: x.x.x.x BDR: y.y.y.y), and any repeating reset loop.
debug ip ospf eventsBroad view — timers firing, interface state changes. Noisy; use when the narrower debugs show nothing.
undebug all / u allRun this the moment you have your answer. Debug output is CPU-expensive and can cause the outage you're diagnosing.

Commands that disrupt — know before you type

CommandWhat it costs you
clear ip ospf processDrops every adjacency on the router and blackholes traffic until they rebuild. Legitimate for forcing a DR re-election or applying a new loopback-derived Router ID — but a change-window action. Clear DROTHERs first, the DR last.
clear ip ospf countersHarmless — resets statistics only.
clear ip route *Flushes the routing table; brief loss while it repopulates. Rarely the right answer.
Changing hello-intervalAuto-adjusts the dead interval on that interface only — the neighbour drops until you match it at the other end.
Changing auto-cost reference-bandwidthHarmless on one router, dangerous across a domain if you stop halfway. All devices, one window.

A workable habit: before any OSPF change, capture show ip ospf neighbor, show ip ospf interface brief and show ip route ospf to a file. After the change, capture the same three and diff them. Nearly every "what did we break?" conversation is settled by that one habit.
